# Полный JSON-лог расчёта остекления

## Цель

Создавать на рабочем столе один машиночитаемый JSON-файл на каждый запуск команды, чтобы установить точную причину включения, исключения или неверной классификации каждого окна, витражной панели и стены-остекления.

## Границы

Логирование временно включено без настройки в UI. Оно не меняет правила расчёта, не прерывает транзакцию и не заменяет обработку исключений. Ошибка записи лога не должна отменять расчёт.

## Содержимое лога

Верхний уровень содержит UTC-время, версию сборки, выбранный режим (Rooms/Spaces), текущий инженерный документ, выбранный архитектурный документ, ID связи и полную матрицу `GetTotalTransform()`. Отдельно фиксируются списки собранных источников: окна, витражные стены и базовые стены-остекления в текущем и связанном документах.

Для каждого целевого Room или Space лог содержит ID, UniqueId, номер, имя, исходные значения восьми параметров площади и результат получения `Solid`. Если `Solid` не получен, фиксируется `NoTargetSolid`: текущая реализация пропускает такой элемент и не перезаписывает его старые значения.

Каждая цель получает шесть `sourcePasses`: `CurrentWindows`, `CurrentCurtainWalls`, `CurrentGlazingWalls`, `LinkedWindows`, `LinkedCurtainWalls`, `LinkedGlazingWalls`. Внутри прохода записывается каждая проверенная сущность, в том числе исключённая фильтрами. Это позволяет отличать «элемент не собран» от «собран, но не отнесён к помещению».

### Окна

Для окна записываются: ElementId, UniqueId, документ-источник, SuperComponent, четыре исходных параметра площади (`ROUGH_HEIGHT`, `ROUGH_WIDTH`, `CASEWORK_HEIGHT`, `CASEWORK_WIDTH`), выбранные max-значения и итоговая площадь. Логируется bounding box, центр и `FacingOrientation` после transform. Затем последовательно фиксируются:

- spatial probes на 150, 300 и 700 мм: `front`, `back`, попадание в целевой Room/Space, найденный другой Room/Space с ID и UniqueId;
- наличие и координаты From/To calculation points, результаты принадлежности и выбранный наружный вектор;
- fallback-луч: начало, конец, количество сегментов пересечения с `Solid`.

### Панели витражей и стены-остекление

Для каждой витражной стены фиксируется наличие `CurtainGrid` и результат фильтра «Наружный витраж». Для каждого fill фиксируются construction type, model group типа панели, model group host-элемента из `FindHostPanel`, итог фильтра `IsCurtainGridFillGlazing`, путь получения bounding box (сам fill, host или geometry fallback), нормаль, площадь `HOST_AREA_COMPUTED`, spatial probes и оба луча к `Solid` с числом сегментов.

Для базовой стены-остекления фиксируются `CurtainGrid`, model group типа стены, результат фильтра «Остекления», `Wall.Orientation`, `HOST_AREA_COMPUTED`, probes и оба луча.

### Направление и запись результата

Для каждого элемента, дошедшего до добавления площади, фиксируются исходный наружный вектор, базисы истинного севера, выбранный bucket, площадь до и после добавления в bucket. После всех шести проходов фиксируются итоговые восемь площадей и результат установки каждого параметра: GUID, старое значение, новое значение, `IsReadOnly` и исключение API при наличии.

Каждая сущность имеет `outcome` (`Counted` или `Skipped`) и код причины. Коды включают `NotOuterCurtainWall`, `NotGlazingMarker`, `HasSuperComponent`, `NoTargetSolid`, `NoArea`, `NoOrientation`, `NoBoundingBox`, `InteriorOpening`, `NoSpatialAssociation`, `NoSolidRayIntersection`, `InvalidDirection`, `ParameterReadOnly` и `ApiException`.

## Файл и обработка ошибок

Файл создаётся в `%USERPROFILE%\\Desktop` с именем `CardinalDirectionGlazing_yyyyMMdd_HHmmss_fff.json`. Лог накапливается в памяти во время вычисления и записывается после commit транзакции либо в `finally` при отмене/исключении. Невозможность создать или записать файл показывается отдельным TaskDialog, но не влияет на уже рассчитанные параметры.

## Проверки

Регрессионные тесты проверяют сериализацию трассы с пространственными probes, причиной исключения и итогом target. Сборка проверяется в R2019–R2026.
