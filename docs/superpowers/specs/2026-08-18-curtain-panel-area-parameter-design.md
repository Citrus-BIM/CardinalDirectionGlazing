# Площадь витражных панелей из выбранного параметра

## Цель и границы

Добавить для витражных панелей отдельную настройку площади из выбранного параметра по аналогии с окнами. Изменение применяется только к элементам Revit runtime-типа `Panel`, которые уже признаются остеклением текущим алгоритмом.

Существующие алгоритмы окон, витражных стен, базовых стен-остекления и редких заполнителей runtime-типа `Wall` не меняются. Для `Panel` резервным источником площади остаётся текущий `HOST_AREA_COMPUTED`.

## Выбор в пользу стабильности

Реализация будет параллельной оконной, но не станет переименовывать или обобщать уже работающие классы `WindowAreaParameter*`. Это намеренно ограничивает область регрессии: оконный поток данных остаётся неизменным, а новый код подключается только в обработку `Panel`.

Единственная общая часть с существующим расчётом панелей — классификатор заполнителя витражной сетки. Текущая логика `IsCurtainGridFillGlazing` выносится без изменения порядка и условий в отдельный сервис и затем вызывается как расчётом, так и каталогом параметров. Благодаря одному классификатору список параметров и фактический расчёт не смогут разойтись по пониманию того, какая панель является остеклением.

## Интерфейс

В существующей группе `Площадь остекления из параметра` добавляется отдельная строка:

- чекбокс `Витражные панели`;
- выпадающий список параметров площади панелей.

Список доступен только при включённом чекбоксе. Если чекбокс включён, но параметр не выбран, запуск расчёта блокируется существующим способом с понятным сообщением пользователю. Настройка окон остаётся отдельной: пользователь может независимо включать и выбирать разные параметры для окон и панелей.

В списке параметры экземпляра и типа отображаются отдельно, например `Площадь стекла (экземпляр)` и `Площадь стекла (тип)`. Одноимённые общие параметры с разными GUID остаются разными вариантами, как в существующей реализации окон.

## Формирование каталога

Каталог строится из текущего документа и всех загруженных связанных документов, уже доступных команде. Для каждого документа обходятся витражные стены и их `CurtainGrid.GetPanelIds()` — тот же источник заполнителей, который использует расчёт.

В каталог допускается элемент, только если одновременно выполнены условия:

1. элемент существует и имеет runtime-тип `Panel`;
2. общий классификатор признаёт его остеклением по текущей логике маркеров;
3. параметр расположен на экземпляре панели или на доступном типе панели;
4. параметр имеет `StorageType.Double`;
5. тип данных определения параметра — `Area`.

Повторное появление одной панели или одного типа из нескольких витражных сеток не должно приводить к повторному сканированию. Отсутствующий связанный документ, удалённый элемент, недоступный тип, пустой `GetPanelIds()` или исключение чтения отдельного элемента пропускаются безопасно и не останавливают формирование каталога.

Общие параметры идентифицируются по области `экземпляр/тип` и GUID. Необщие параметры — по области и имени. Проверка `Area` выполняется совместимо с Revit API 2019–2026: `Definition.ParameterType` в старых API и `Definition.GetDataType()`/`SpecTypeId.Area` в новых.

## Сохранение и восстановление

В `CardinalDirectionGlazingSettings.xml` добавляются отдельные поля панелей:

- `UseCurtainPanelAreaParameter`;
- `CurtainPanelAreaParameterName`;
- `CurtainPanelAreaParameterScope`;
- `CurtainPanelAreaParameterGuid`.

Для общего параметра восстановление и чтение выполняются прежде всего и строго по GUID в сохранённой области. Если GUID не найден, одноимённый параметр не подставляется. Для необщего параметра без GUID восстановление выполняется по имени и области.

Новые свойства получают безопасные значения по умолчанию. Поэтому старые XML без этих полей загружаются с выключенной настройкой панелей и сохраняют прежний расчёт.

## Поток расчёта площади

Обход витражных стен, получение `CurtainGrid`, определение принадлежности помещению или пространству, вычисление направления и запись итоговых сумм остаются текущими.

Изменяется только точка получения площади уже принятого заполнителя `Panel`:

1. Сначала читается существующая резервная площадь из `HOST_AREA_COMPUTED` тем же методом, что и сейчас.
2. Если настройка панелей выключена, сразу используется резервная площадь.
3. Если настройка включена, параметр ищется только в выбранной области — на экземпляре `Panel` либо на его типе в документе панели.
4. Для сохранённого общего параметра разрешается только точное совпадение GUID. Поиск по имени применяется только к выбранному необщему параметру.
5. Перед чтением повторно проверяются тип данных `Area` и `StorageType.Double`; каталог не считается достаточной гарантией, поскольку разные экземпляры и связанные документы могут отличаться.
6. Значение параметра используется, только если оно конечное и строго больше нуля.
7. При отсутствующем параметре или документе/типе, неверном типе данных или хранения, исключении чтения, значении `0`, отрицательном, `NaN` или бесконечности используется ранее полученный `HOST_AREA_COMPUTED`.
8. Полученная площадь без дополнительного преобразования единиц передаётся в существующий поток распределения по сторонам света и добавляется в те же итоговые суммы.

Для заполнителя runtime-типа `Wall` выбранный параметр панелей никогда не читается: он полностью проходит прежний путь и использует прежнюю площадь. Оконный `GetWindowArea` и его fallback высота × ширина не изменяются.

## Статистика и диагностика

При включённой настройке панелей итоговое сообщение дополнительно показывает:

- сколько витражных панелей рассчитано по выбранному параметру;
- сколько витражных панелей рассчитано по `HOST_AREA_COMPUTED` из-за отсутствующего или некорректного значения.

Панель регистрируется в статистике только после успешного добавления её площади в направление. Ключ уникальности — документ панели плюс `UniqueId`, поэтому повторные проходы не учитывают один элемент несколько раз.

Диагностика панели получает имя, область и GUID выбранного параметра, прочитанное значение, фактически использованный источник площади и причину fallback. Это не меняет включение или формат существующего JSON-лога за пределами добавления полей к записи панели.

## Обработка ошибок

Ошибки чтения параметра являются локальными для панели и всегда приводят к `HOST_AREA_COMPUTED`, а не к остановке команды. Null-документы связей, null-типы, невалидные `ElementId`, отсутствующие определения и параметры безопасно обрабатываются.

Ошибки существующей геометрической или пространственной обработки не маскируются новым кодом: поведение таких случаев остаётся прежним. Новый механизм не открывает транзакций, поскольку только читает параметры; транзакция записи результатов не меняется.

## Проверки и регрессия

Разработка фиксируется тестами до изменения рабочего кода. Минимальный набор автоматических сценариев:

1. Выключенная настройка `Panel` всегда возвращает `HOST_AREA_COMPUTED`.
2. Положительное конечное значение выбранного параметра заменяет `HOST_AREA_COMPUTED`.
3. Отсутствующий параметр, неверный `StorageType`, не-`Area`, `0`, отрицательное, `NaN` и бесконечное значение приводят к fallback.
4. Экземплярный и типовой параметры читаются из правильной области.
5. Общий параметр читается и восстанавливается строго по GUID; одноимённый GUID не подменяет отсутствующий сохранённый GUID.
6. Необщий параметр восстанавливается по имени и области.
7. Каталог включает только принятые текущим классификатором runtime-`Panel` из текущего и связанных документов.
8. Каталог не включает runtime-`Wall`, непрозрачные панели и параметры не типа `Area`/не `Double`.
9. Старый XML без полей панелей сохраняет выключенный режим и прежний результат.
10. Новые поля XML сохраняются и восстанавливаются.
11. Статистика различает параметр и fallback и дедуплицирует панель по документу и `UniqueId`.
12. Существующие тесты окон подтверждают, что их поток не изменился.
13. Регрессионные тесты подтверждают неизменность расчёта runtime-`Wall`, витражных стен и базовых стен-остекления.
14. XAML содержит независимые элементы окон и витражных панелей с корректным состоянием доступности.
15. Все тесты проекта проходят, а конфигурации `R2019`–`R2026` успешно собираются.

После реализации выполняется отдельное независимое ревью фактического потока данных от выбранного параметра до итоговой площади по сторонам света. Слияние и отправка выполняются только после устранения найденных проблем и повторного полного цикла тестов и сборок.

## Вне объёма

- заполнители витражной сетки runtime-типа `Wall`;
- двери и окна, вставленные в витражную сетку;
- витражная стена как единый источник площади;
- базовые стены-остекления;
- единый параметр сразу для окон и панелей;
- переработка визуального дизайна окна за пределами добавления строки панелей;
- сопоставление разных параметров разным типам панелей в одном запуске.
